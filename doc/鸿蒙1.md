## 0. 结论速览（TL;DR）

| 决策项 | 结论 |
| :--- | :--- |
| 推荐路线 | **路线一（ArkUI + ArkWeb WebView 壳 + JSBridge）先行上架 MVP**，二期对高频页做"原生混合增强"，**不做全量原生重写** |

### 1.2 页面结构与"移动端形态"现状

```
/routes           行程规划（高德地图 + AI 生成路线）

/search           全局搜索（RAG）
/vr-recognize     VR 即拍即识（getUserMedia 相机 + 多模态识别）

/admin/*          运营后台（数据大屏、景点/知识库/数字人管理）
/api/*            41 个 Route Handlers
```

关键形态判断：**本项目虽然用 Next.js，但 UI 已经是"移动 App 形态"**——
[LayoutShell.tsx](file:///e:/Code/AI/Start/Web/AI-guide/src/components/layout/LayoutShell.tsx) 提供底部 5 Tab（首页/热门景点/AI数字人导游/行程规划/我的）+ PC 侧边栏双导航；全部业务界面在 `src/components/screens/*Screen.tsx` 中以 SPA 屏幕组件实现；已使用 `env(safe-area-inset-bottom)` 做刘海屏避让；已有 `data-accessibility-mode`（普通/银发/儿童三模式）机制。

**对鸿蒙的影响**：这是"WebView 壳"路线成立的根本原因——H5 本身长得就是一个原生 App，装进 ArkWeb 后与原生应用观感几乎一致；同时说明若走原生重写，页面清单（17 个 Screen + 5 个 Admin 页）就是重写工作量清单。

### 1.4 数据库、登录态与缓存

- **PostgreSQL + Drizzle**（`src/lib/db/` schema / migrations / queries，托管库（云端 PostgreSQL））：典型服务端资产，**结论：保留云端，不迁移**。鸿蒙端任何"本地数据"需求（草稿箱、离线景点、会话缓存）用 `@kit.ArkData` Preferences / RelationalStore 实现，仅作为**缓存层**。
- **登录态**：`@eazo/sdk` 的 `auth`（LayoutShell 中 `useEazo((s) => s.auth.user)` 守卫）。会话凭据存于浏览器环境。WebView 路线：开启 `domStorageAccess(true)` + cookie 持久化（ArkWeb 默认随应用沙箱持久化）即可复用；原生路线：改用 `@kit.UniversalKeystoreKit` 安全存储 token。
- **本地缓存现状**：`localStorage`（`accessibility_mode` 三模式偏好等）+ Service Worker CacheFirst。鸿蒙端映射：`localStorage → Preferences`，`SW 缓存 → rawfile 内置资源 + 手工 HTTP 缓存`。

### 1.5 AI / RAG / 语音 / 地图 / 静态资源

- **RAG**：`src/lib/ai/embedding.ts`（SiliconFlow Embedding）+ 混合重排 + 防幻觉约束，纯服务端逻辑，鸿蒙端零改动。
- **模型接入**：DeepSeek-V4（`src/lib/deepseek-v4/chat.ts`）、StepFun（`stepfun/` chat/asr/tts/recognize、`stepfun-vision/`）、讯飞 TTS（`xfyun-tts.ts`）、Eazo SDK。均为**服务端持 Key 调用**——这正是鸿蒙端的安全边界：密钥绝不下发端侧。
- **语音链路**：前端 `Web Speech API`（`QAScreen.tsx` 600 行前后：分句合成、口型驱动 Live2D）+ `MediaRecorder`（录音上传 `/api/qa/stt`）。鸿蒙约束：ArkWeb 的 `speechSynthesis` 依赖系统音色，中文效果与可用性**需真机验证**；机会：Core Speech Kit 提供端侧离线 TTS/STT，可通过 JSBridge 替换，弱网景区体验更好。
- **地图**：高德 JSAPI（Web 专属）+ `_AMapSecurityCode` 安全密钥 + turf 球面计算。约束：**高德无 HarmonyOS NEXT 原生 SDK**；路线一不受影响（WebView 渲染），路线二需评估华为 Map Kit 迁移成本（坐标体系 GCJ-02 一致，API 形态不同）。
- **相机**：`CameraRecognize.tsx` 用 `getUserMedia`；ArkWeb 需 `onPermissionRequest` 联动系统相机权限（已在 `harmony/Index.ets` 示例）。
- **静态资源**：`public/image`（webp 主视觉）、`public/images/spots`（94 张景点图 + route 图）、`public/sentio`（Live2D 模型与角色资源）、`manifest.json`、`sw.js`、`offline.html`。`next.config.ts` 设置了 `images.unoptimized`——**对鸿蒙友好**（无 Next Image 优化服务依赖，WebView/CDN 直接可用）。同步策略见 `harmony/sync-resources.ps1`（只复制、不改动）。

### 1.6 既有"移动端转换方案"与文档脉络

- **PWA**（manifest + sw.js + offline.html）：当前移动端主交付形态（"添加到桌面"）。与鸿蒙关系：PWA 的 Web App Manifest 在 HarmonyOS 浏览器/ArkWeb 中不产生安装语义，鸿蒙的分发等价物是**元服务（原子化服务）+ 万能卡片**（`鸿蒙.md` §2.4 已规划）。
- **Capacitor/Cordova**：项目未引入；**Capacitor 官方不支持 HarmonyOS NEXT**，鸿蒙侧对应能力需自研 ArkWeb 壳（即本方案路线一），社区另有基于 ArkWeb 的 capacitor-harmony 移植可作后期调研项，MVP 不依赖。
- **静态导出（`next export`）**：不适用——项目重度依赖 Route Handlers / SSR API / middleware 鉴权，导出仅得空壳。若未来做"离线 H5 包"，只导营销页/景点详情等纯静态子集，放 rawfile 加载。
- **文档既有承诺**：`doc/ok/决赛.md` 已写明"按 Harmony.md 架构完成 ArkTS + JSBridge 混合动力包打包并在 AppGallery 提交上架"——本方案即该规划的执行落地版本。

### 1.7 打包与上架现状

- 现网：Vercel（`traveler-pro.vercel.app`），`vercel.json` 配置 Cron（`/api/notifications/cron/daily-digest`）。
- 鸿蒙端上架依赖此线上地址；**因此 Vercel 服务的可用性就是鸿蒙 App 的可用性**，需在生产环境加健康监控（见 §6）。

### 1.8 对鸿蒙适配的关键约束与机会汇总（含一处必须处理的安全问题）

**约束**
1. ArkWeb ≠ 完整 Chrome：Service Worker、speechSynthesis、部分 CSS 新特性需真机逐项验证。
2. 高德 JSAPI 仅 Web 形态存在；原生路线地图能力需换 Map Kit。
3. Live2D 无鸿蒙官方 SDK；原生路线数字人渲染是最大重写成本项。
4. HarmonyOS NEXT 无 AOSP 兼容层，APK 方案（含 Capacitor 安卓产物）全部失效。
5. **⚠️ 密钥明文风险**：`next.config.ts` 的 `ENV_DEFAULTS` 内置了 `DATABASE_URL`（含账号密码）与 `EAZO_PRIVATE_KEY` 明文并已提交仓库。虽为服务端变量，但属于上架审核隐私合规隐患（华为审核会关注数据泄露风险）。**建议尽快**：迁移至 Vercel Dashboard 环境变量、轮换数据库密码并从 git 历史清除。此项属于原项目安全整改，**不在本鸿蒙工程内代改**。

**机会**
1. UI 已是移动 App 形态 + `images.unoptimized` + 全 HTTPS → WebView 壳成本极低。
2. 端侧 Core Speech Kit / Core Vision Kit 可补齐 Web 短板（离线语音、拍照预处理），契合"景区弱网"卖点。
3. 元服务 + 万能卡片 + 碰一碰，天然匹配"扫码即用导游"场景（比 App 分发更轻）。
4. 分布式跨端迁移（手机→车机/平板接力）是差异化亮点，`鸿蒙.md` 已规划，工程已预留 `continuable: true` 与 `onContinue`。

## 2. 鸿蒙技术路线选择

### 2.1 路线一：ArkUI + ArkWeb WebView 壳 + JSBridge（混合轻壳）

把现有 H5（Vercel 线上版）装入 `Web` 组件，注入 `bridge.js` 桥接原生能力。

- **适用条件**：MVP 快速上线、功能面广（17 屏）、迭代频率高、团队 Web 强/ArkTS 弱。
- **开发成本**：约 **2~3 周**（壳工程 3 天 + JSBridge 能力 1 周 + 适配与真机测试 1 周）。
- **性能**：首屏依赖网络（预取 + rawfile 兜底可缓解）；列表动画、Live2D 在 ArkWeb（Chromium 内核）内流畅；内存比原生高约 100~200MB。
- **上架难度**：低。但**纯 Web 壳有被审核判定"网页套壳、体验不达标"的风险**，需用 JSBridge 深度集成系统能力（相机/定位/TTS/卡片/分享/通知）证明原生价值。
- **改造范围**：原 Web 项目 **0 行强制改动**；可选增强：H5 内以 `window.__harmony__` 探测鸿蒙环境做渐进增强。
- **风险点**：speechSynthesis/Service Worker 兼容性；线上地址故障 = App 白屏（已设计原生兜底页）。

### 2.2 路线二：ArkTS + ArkUI 原生重写

按 `鸿蒙.md` 5 大核心技术全原生实现（ArkUI 组件 + Location/Map/Speech/Vision Kit + 卡片 + 分布式）。

- **适用条件**：长期产品化、追求帧率/功耗/离线体验、要上分布式接力与元服务完整形态。
- **开发成本**：**3~6 人月起步**：17 个 Screen 重写 + Tailwind 体系重建为 ArkUI Token + Framer Motion → ArkUI 转场 + **Live2D 需 C++ Cubism Native + NAPI 移植（最高风险单项）** + 高德 → Map Kit 迁移 + SSE/上传全部用 `@kit.NetworkKit` 重写。
- **性能**：最优（冷启动、动画、内存、后台音频均系统级）。
- **上架难度**：最低（原生体验审核最稳），且可同步申报元服务流量扶持。
- **风险点**：Live2D 移植无官方鸿蒙 SDK 支撑；RAG 问答 UI 的流式打字机+口型联动逻辑复杂；双端（Web/鸿蒙）UI 从此分叉，维护成本翻倍。

### 2.3 路线三：React Native for OpenHarmony（RNOH）/ 混合

华为已将 RN 运行时（RNOH，`@rnoh/react-native-openharmony`）上架 ohpm，可复用 React 组件思维在鸿蒙渲染原生 UI。

- **适用条件**：已有 RN 工程或计划 iOS/Android/鸿蒙三端统一时。
- **本项目不适配的原因**：现有代码是 **React-DOM（Web）而非 React-Native**，组件（shadcn/Base UI/Tailwind/Framer Motion/Live2D-WebGL/高德 JSAPI）没有一个是 RN 组件——"迁移到 RNOH"实际等于"用 RN 语法重写整个前端"，成本接近路线二， yet 生态（reanimated、地图、Live2D RN 库）在 RNOH 上的支持反而更不完整。
- **结论**：仅当未来出现"三端统一"强诉求才值得启动，当前不推荐。

### 2.4 对比矩阵与推荐

| 维度 | 路线一 WebView 壳 | 路线二 ArkTS 原生 | 路线三 RNOH |
| :--- | :--- | :--- | :--- |
| MVP 上线 | ★★★★★（2~3 周） | ★（2~3 月） | ★★ |
| 性能/体验 | ★★★ | ★★★★★ | ★★★★ |
| 开发成本 | 低 | 极高 | 高 |
| 原项目改动 | **0** | 前端全废重写 | 前端全废重写 |
| Live2D 数字人 | ✅ WebView 直接跑 | ⚠️ C++/NAPI 移植 | ⚠️ 需 RN webview 兜底 |
| 高德地图 | ✅ JSAPI 直接跑 | ⚠️ 换 Map Kit | ⚠️ 同左 |
| SSE 流式 | ✅ fetch stream | ✅ http chunk | ✅ |
| 后台音频/通知 | ⚠️ 需 bridge 增强 | ✅ 系统级 | ✅ |
| 元服务/卡片 | ⚠️ 可后置 | ✅ 完整 | ⚠️ 支持有限 |
| 套壳审核风险 | 中（靠 bridge 化解） | 无 | 低 |
| 双端维护成本 | 低（一套 H5） | 高（两套 UI） | 高 |

**推荐：路线一 → 渐进混合。**
阶段 1 用壳方案 2~3 周内上架 AppGallery，占住鸿蒙生态位；阶段 2 只把"体验短板页"（FM 后台播放、QA 语音链路）用 ArkTS 原生页 + Navigation 路由嵌进壳工程（同一 App 内 WebView 页与原生页混合导航），逐步逼近路线二收益而不付全量重写成本。路线三永久关闭，除非未来做三端统一产品。

## 3. 具体跨端转换步骤（路线一为主，标注阶段 2 增强项）

### 3.1 创建鸿蒙工程

1. DevEco Studio 5.0+ 新建 Empty Ability 模板工程（Stage 模型，ArkTS），SDK 选 API 12+。
2. 将模板工程业务文件替换/合并为 `harmony/app/` 中已生成的骨架（`app.json5`、`module.json5`、`EntryAbility.ets`、`Index.ets`、`ApiConfig.ets` 均按本项目定制过）。
3. `bundleName` 建议使用已备案域名反写（如 `app.traveler.pro`），与华为开发者账号主体一致。

### 3.2 静态资源整理与复用

- 原则：**只复制、不移动、不改名**。执行 `powershell -File harmony\sync-resources.ps1`：
  `public/image`、`public/offline.html`、`public/manifest.json` → `entry/src/main/resources/rawfile/assets/`；`harmony/web-bridge/bridge.js` → `rawfile/bridge.js`。
- 景点图（`public/images/spots`，94 张 webp ≈ 体积可观）**默认不同步**——MVP 继续走线上 URL；离线包需求（会员"离线地图包"卖点）出现时再做精选子集同步。
- 原 `public/` 目录不做任何改动；鸿蒙包体内资源以 `resourceManager.getRawFileContent` 读取。

### 3.3 路由与移动端交互（TabBar/抽屉/弹窗）

- **MVP 策略：H5 内部导航全部保持现状。** `BottomTabBar`（5 Tab）、侧滑抽屉（SidebarNav 的移动端形态）、`PointsInviteModal`、sonner toast 等均运行在 WebView 里，无需迁移。
- 壳层只负责 4 类"系统级导航"：
  1. **返回手势**：`Index.ets onBackPress()` → `controller.accessBackward()/backward()`，H5 历史栈空时才退出（已实现）。
  2. **桌面卡片/碰一碰深链**：`onNewWant` 取 `targetRoute` 存 AppStorage → bridge 广播 `harmony:navigate` 事件 → H5 用 `window.location` 切屏（增强阶段接 `@kit.AbilityKit` 深链 Uri skills）。
  3. **Tab 与原生页共存**（阶段 2）：将 `/fm`、`/qa` 语音模式改为 ArkTS `Navigation + NavDestination` 原生页，WebView 与原生页间用 `EventHub` 通信。
  4. **弹窗**：原生权限弹窗、升级弹窗由壳层承载，业务弹窗留在 H5。

### 3.4 安全区 / 刘海屏 / 状态栏 / 导航条 / 手势

- `EntryAbility` 已实现：`setWindowLayoutFullScreen(true)` 沉浸式 + `getWindowAvoidArea(TYPE_SYSTEM)` 读取刘海/状态栏高度 + `on('avoidAreaChange')` 动态监听（旋屏/挖孔变化）。
- 避让值双通道下发：① ArkWeb `onSafeAreaAdjust` 映射到 WebView 的 `viewport-fit=cover` inset；② `bridge.applySafeArea()` 注入 CSS 变量 `--safe-area-inset-*`。原 H5 中 `env(safe-area-inset-bottom)`（LayoutShell 第 100 行）在 WebView 内原生生效，无需改代码。
- 侧边返回手势：系统手势与 H5 横滑冲突，`horizontalSwipeAccess(false)` 已禁 WebView 横滑回退，交由系统返回手势统一处理。

### 3.5 多设备尺寸（手机 / 折叠屏 / 平板）

- `deviceTypes` 已声明 `phone / tablet / 2in1`。
- H5 本身是响应式（Tailwind 断点），WebView 自动适配；折叠屏重点验证两处：
  1. 折叠↔展开瞬间的 `avoidAreaChange` 重布局（已监听）；
  2. 悬停态（Flex Mode）上半屏视频/下半屏操作的分屏体验（阶段 2 用 ArkTS `FolderStack`/`display.on('foldStatusChange')`）。
- 平板建议：Web 版现有 `md:` 断点（≥768px）自动呈现 PC 侧边栏形态，壳层按 `windowWidthBreakpoint` 决定是否隐藏手机 TopBar。

### 3.6 深色模式 / 字体缩放 / 无障碍（银发·儿童模式）

- **深色模式**：现有 `next-themes` 在 WebView 中跟随系统 `prefers-color-scheme`，ArkWeb 默认继承应用深色配置，**零改造**；需真机验证 Live2D 背景与深色底对比。
- **字体缩放**：鸿蒙系统字体缩放（`fontScale`）会作用于 WebView，需回归测试银发模式（其本身已有大字逻辑）与系统放大的叠加效果，避免过大溢出——bridge 暴露 `getContext().config.fontScale` 供 H5 判断封顶。
- **三模式（normal/senior/kid）**：状态存于 H5 `localStorage`，WebView 持久化开启即可跨启动保留；阶段 2 若做原生页，模式经 AppStorage 同步（`EntryAbility.onContinue` 已带 `accessibilityMode` 字段）。
- **无障碍**：H5 的 aria 标签在 ArkWeb 内可被鸿蒙 ScreenReader（导能触摸）读取；原生页按 `鸿蒙.md` §2.1 用 `accessibilityText/Level` 补齐。

### 3.7 系统能力迁移（相机/录音/播放/定位/权限）

| 能力 | Web 现状 | 鸿蒙路线一做法 | 阶段 2 原生化 |
| :--- | :--- | :--- | :--- |
| 相机拍照识别 | `getUserMedia`（CameraRecognize.tsx） | ArkWeb `onPermissionRequest` 授予 CAMERA + 系统弹窗（已实现）；若兼容性差 → bridge `capturePhoto` 走 Camera Kit 回传 base64 | Camera Kit + Core Vision Kit 端侧预处理 |

| 语音播报 TTS | Web Speech API 分句 + Live2D 口型 | **真机验证 ArkWeb speechSynthesis**；不佳则 bridge `tts` → Core Speech Kit，口型数据（振幅）回传 H5 驱动 | AudioRenderer + 系统 TTS |

### 3.8 网络 / SSE / 离线 / 重试 / 弱网

- **路线一**：网络栈就是 WebView 的 Chromium——现有 `fetch` SSE 解析代码不变，`/api/qa/chat` 的 `text/event-stream` 流式打字机体验完整保留。
- **路线二原生页 SSE 示例**（阶段 2，`@kit.NetworkKit` 分块接收手动解析）：

```typescript
import { http } from '@kit.NetworkKit';

export async function streamChat(body: string, onDelta: (t: string) => void): Promise<void> {
  const req = http.createHttp();
  let buf = '';
  req.on('dataReceive', (chunk: ArrayBuffer) => {
    buf += new util.TextDecoder('utf-8').decodeToString(new Uint8Array(chunk));
    let idx: number;
    while ((idx = buf.indexOf('\n\n')) >= 0) {       // SSE 帧边界
      const frame = buf.slice(0, idx); buf = buf.slice(idx + 2);
      for (const line of frame.split('\n')) {
        if (line.startsWith('data: ') && line !== 'data: [DONE]') {
          try { onDelta(JSON.parse(line.slice(6)).content ?? ''); } catch (_) { /* 忽略心跳帧 */ }
        }
      }
    }
  });
  await req.requestInStream(ApiConfig.API_BASE + ApiConfig.QA_CHAT_STREAM, {
    method: http.RequestMethod.POST,
    header: { 'Content-Type': 'application/json', 'Cookie': await getTokenCookie() },
    body,
  });
}
```

- **离线与缓存**：WebView 开启 `cacheMode(CacheMode.ENABLE_DEFAULT)`；关键只读页（景点详情、路线列表）由 bridge 写 `RelationalStore` 快照，断网时壳层 `onErrorReceive` → 加载 `rawfile/offline.html`（复用原项目同名文件）并提供"查看已缓存内容"入口。
- **弱网重试**：GET 类接口在 H5 层已有 loading 态；原生层增补 `connection.on('netAvailable')` 网络恢复自动 `refresh()`（阶段 2）。
- **域名白名单**：壳层 `onInterceptRequest` 只放行 `traveler-pro.vercel.app`、高德 CDN、Eazo 域名，其余外链跳系统浏览器（安全合规 + 审核加分）。

### 3.9 Next.js API 的架构定位：保留云端（混合架构）

```
┌─ 鸿蒙 App (harmony/) ─────────────┐      ┌─ 云端（原样保留）────────────────┐
│ ArkWeb 壳 ── JSBridge ── ArkTS 原生页 │ HTTPS/SSE │ Next.js Route Handlers @ Vercel │
│   (H5 业务 UI)   (系统能力)  (阶段2)  │ ───────▶ │  RAG / DeepSeek / StepFun / DB  │
│ Preferences / RelationalStore (缓存) │      │  PostgreSQL+Drizzle / MCP / Cron │
└──────────────────────────────────┘      └──────────────────────────────────┘
```

- **不迁移**：Route Handlers、Drizzle/PG、模型密钥、MCP Server、Vercel Cron——全部原地不动，Web/PWA 用户继续直接访问。
- **鸿蒙端直连**：即直连 Vercel 线上 API（无独立"鸿蒙后端"）；若后续担心 Vercel 在大陆的访问质量，备选方案是把 API 层原地重部署到华为云 FunctionGraph/ESC（Drizzle 迁移脚本、Zod 校验零改动），此项属于运维决策，不影响本工程。
- **本地服务**：不引入（无 Node 运行时诉求，端侧推理由 Core Kit 承担）。

### 3.10 保证原 Web 项目独立运行（隔离措施）

1. 所有鸿蒙文件仅位于 `harmony/` 与本文档；不新增/修改 `src/`、`public/`、`doc/`、根配置任何文件。
2. `harmony/app` 无 npm 依赖，不参与 `bun dev/build`，也不被 ESLint/tsc 工程（根 `tsconfig.json` 的 `include` 仅 `src`）扫描。
3. 资源同步为**单向复制**（public → rawfile），`public/` 永远是唯一事实源。
4. H5 侧的鸿蒙增强（如 `window.__harmony__` 探测）是**可选渐进增强**：脚本不存在时 Web/PWA 行为完全不变。
